# Аудит Bitrix24 (коробка) — ТОЛЬКО ЧТЕНИЕ

## Абсолютные правила
1. **Никаких изменений действующей системы** (CRM, роботы, БП, права, пользователи, настройки, файлы, БД, сервер)
   без явного разрешения пользователя в текущей сессии на конкретное действие. Аудит выдаёт рекомендации —
   внедряет их человек.
2. REST — только через `scripts/b24_readonly.py` (белый список методов чтения, `batch` запрещён, журнал вызовов).
   Не использовать curl/браузер/другие клиенты для `/rest/…`. Хук безопасности спросит подтверждение на любые
   обращения к `/rest/` вне этого скрипта.
3. URL вебхука — секрет: только из переменной окружения `B24_WEBHOOK_URL`; не печатать, не сохранять в файлы,
   не коммитить. После аудита — рекомендовать удалить/перевыпустить вебхук.
4. Персональные данные сотрудников и клиентов (152-ФЗ): выгрузки хранить локально, в отчёт — только агрегаты и
   обезличенные примеры; не загружать во внешние сервисы.
5. Подключение к серверу (SSH, БД, админка) — только если пользователь сам предоставил доступ и разрешил;
   по умолчанию работать с выгрузками/скриншотами, которые даёт администратор.

## Подготовка доступа (делает администратор; инструкция для пользователя)
Read-only области доступа в Bitrix24 нет, поэтому защита многоуровневая (`references/access-setup.md`):
отдельный пользователь-аудитор с правами CRM «только чтение» → входящий вебхук от его имени со scope
`crm, user_brief, department` (+ `task` при необходимости) → для шаблонов БП — временный вебхук администратора
только со scope `bizproc`, удаляемый сразу после аудита → белый список в скрипте → по возможности ограничение
пути `/rest/<id_аудитора>/` по IP в nginx.

## Что смотреть (`references/audit-checklist.md`)
- CRM: воронки (`crm.category.list`), стадии (`crm.status.list`), поля и пользовательские поля, смарт-процессы.
- Автоматизация: **роботы и триггеры на стадиях через REST не читаются** → аудит в интерфейсе (по чек-листу,
  скриншоты от администратора); шаблоны БП — `bizproc.workflow.template.list` (нужен админ-вебхук `bizproc`).
- Пользователи и структура: `user.get`, `department.get`; роли и права CRM — в интерфейсе.
- Интеграции: список входящих/исходящих вебхуков и приложений, владельцы, scope.
- Почта, телефония, открытые линии — по интерфейсу/выгрузкам.
- Сервер: «Проверка системы», резервное копирование и тест восстановления, обновления, панель безопасности,
  сканер безопасности, 2FA администраторов, журнал событий — по отчётам/скриншотам.

## Примеры
```bash
python ${CLAUDE_SKILL_DIR}/scripts/b24_readonly.py scope
python ${CLAUDE_SKILL_DIR}/scripts/b24_readonly.py crm.category.list --param entityTypeId=2 --out audit/categories.json
python ${CLAUDE_SKILL_DIR}/scripts/b24_readonly.py crm.status.list --all --out audit/statuses.json
python ${CLAUDE_SKILL_DIR}/scripts/b24_readonly.py crm.deal.fields --out audit/deal-fields.json
```
Документация методов — официальный MCP документации Bitrix24 (`b24-dev-mcp`, только справка, без доступа к данным).

## Отчёт (`references/report-template.md`)
Резюме → карта процессов (воронки × стадии × автоматизация) → находки (серьёзность, доказательство, риск,
рекомендация, кто внедряет) → права и безопасность → резервное копирование/обновления → план внедрения
рекомендаций (с обязательным подтверждением каждого изменения).
Входящие лиды разбирает отдельный навык пользователя `lead-triage`.
